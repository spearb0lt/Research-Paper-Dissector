Extraction pipelines, one per kind

What happens inside the single box marked Parse on the architecture sheet. A PDF has no paragraphs, no tables and no figures in it: it has glyphs at coordinates, ruling lines, and image objects. Everything below is the work of turning that back into things a reader named. Every constant shown is the real value from the module beside it.

0  The order the fast parser does things, and why that order

FastParser.parse(). The sequence is not arbitrary: three steps exist only because a later step needs their output, and moving them breaks things that look unrelated.

1. Table bands, first

tables.table_bands(page)

Before any text is grouped. A ruling line is the only reliable signal that a caption has ended and a table has begun. Without this, a caption set in body font keeps absorbing the table's own rows and ends up with a bounding box overlapping the table it labels.

→

2. Collect spans

_collect_spans

Every span with its font, size, weight, position and per font character counts. The font census is collected here once and paid for by heading detection, equation detection and margin detection alike.

→

3. Three page statistics

_body_font_size · body_fonts · _body_width

The modal body size, the set of fonts that carry body text, and the body column width. Every classification below is relative to these, so a paper set in 9pt and one set in 12pt are read the same way.

→

4. Group and classify

_elements_from_spans · _classify

Spans become runs, runs become elements. Sections attached, then figures and tables extracted, merged, and sorted by page and vertical position to fix reading order.

→

5. Link, split, link

_link_captions · split_references · link_markers

Captions paired with what they label. Then sections must be settled first, because splitting applies only to the references section, and only _attach_sections knows which elements are in it.

1  Text: paragraphs, headings and list items

Runs of prose

parse/fast.py → _elements_from_spans

Glyph spans to a paragraph

Detect

Consecutive spans accumulate into one run while they share a page, a column and a font size.

→

Break the run on any of

A vertical gap of ≥ line_height × 0.9, about one blank line.

Crossing a table band.

is_formula changing between one line and the next.

→

Classify the run

Heading: at most 140 characters and either size ≥ body + 0.8 or bold at ≥ body - 0.2, and it does not end like prose.

List item: starts with a bullet or an enumerator.

Otherwise a paragraph.

→

Level and margin

Heading level from size above body: +5.0 is 1, +2.5 is 2, +0.8 is 3, else 4.

Text inside the outer 5.5% of the page is a running head or a page number, not prose.

Sections

parse/sections.py

Headings to the sections a reader asks about

Strip the numbering

Leading 3, 3.2, IV, A.1, Appendix B removed before matching.

→

Lexical, not learned

"Methods", "Methodology", "Materials and Methods", "Approach", "Our Model" all reach the same section. A classifier here would sit on the parse path, be wrong in ways nobody could debug, and buy very little.

→

Order matters

"Related Work" contains work and "Experimental Setup" contains experiment, so the more specific patterns are tested first.

→

A miss is survivable

An unmatched heading falls back to UNKNOWN. The element still indexes and still retrieves; only the section filter loses it.

2  Tables, the hardest one

Scientific papers use booktabs: rules above the header, below the header and at the foot, and no vertical rules at all. That breaks every finder that looks for intersecting lines, and it breaks the usual fallback of inferring both axes from whitespace. Both failures were measured before this was written: pdfplumber and PyMuPDF's own find_tables each turned body text on page 3 of "Attention Is All You Need" into a 22 by 8 table of word fragments.

Structure from rules

parse/tables.py

Constants set by sweep, not by taste

1. Horizontal rules

A rule narrower than 10% of the page is a leader dot or an underline, not a table.

→

2. Group into a band

Rules whose x-extent matches to 80% and which sit within 420 pt of each other form one band.

Two or more aligned rules is what a table looks like and what a paragraph never does. This step alone removes the false positives.

→

3. Rows

Words cluster into rows by vertical centre, within 0.55 of the median glyph height.

→

4. Columns by projection

Every word is projected onto the x-axis at 0.5 pt buckets. A column boundary is a run no word covers in ≥ 90% of rows and at least half a character wide.

A results table is column aligned by construction, so these gaps are real and sharp.

→

5. Tidy

Wrapped header lines merged at 0.72 line spacing, stray headings dropped at 2.2, prose rows rejected.

When structure fails

fast.py → _extract_tables

Emit it anyway, and say so

Confident

Grid stored as cells, plus markdown for the prompt and HTML for nothing: the UI renders from the grid, never from parser produced HTML.

→

Not confident

The table is still emitted, with structure_confident false and its region rendered as an image.

A table a reader can see and a vision model can read beats a table that silently went missing.

→

Carried into the prompt

The chunk says in words that the column structure was inferred and that the image is authoritative, so the model does not state a guessed number as fact.

→

Known loss

A header set above the toprule is outside the band and is read as caption instead. Table 2 of the Transformer paper is laid out this way: rows and column count correct, names in the caption rather than the grid.

3  Figures, two passes because there are two kinds

A photograph is an embedded image object and can be extracted losslessly. A chart drawn with vector primitives, which is most charts matplotlib or TikZ produce, has no image object at all and has to be rasterised from the region a caption points at.

Pass 1: embedded

fast.py → _extract_figures

Lossless, from the image objects

Every image xref

Decoded to PNG. CMYK is converted to RGB first, because CMYK has no PNG encoding.

→

Reject the furniture

Smaller than 48 × 48: a rule, a logo or a background texture.

Larger than 92% of the page: a scan or a watermark, not a figure.

→

Dedupe by digest

The same bytes on twelve pages, a journal logo, store and appear once.

→

Store

Content addressed PNG, with its true pixel dimensions and its rectangle on the page.

Pass 2: vector

fast.py → _render_vector_figures

Rasterise what has no image object

Start from the caption

Only captions labelled Figure, Fig, Chart or Scheme. The figure sits above its caption in every convention this will meet.

→

Find the ceiling

Scan everything above, elements and already found figures alike, for the nearest thing that overlaps the caption's column by more than 30%.

Searching only elements was a real bug: already extracted figures were invisible, so two figures on one page were cropped as one.

→

Reject and render

Skip a region under 40 × 40, or one overlapping an embedded figure by more than 50% either way.

Otherwise render the clip at FIGURE_SCALE = 2.0.

→

Honest about it

The crop is a guess, and extra.source records rendered against embedded. A slightly over-cropped figure beats a missing one, and the quality report counts them.

Captions

fast.py → _link_captions

Pair each with what it labels

Recognise

A run matching Figure 3, Table 2, Equation 4 becomes a caption element carrying a normalised label.

→

Conventional side first

A figure caption sits below its figure, a table caption above its table. Enough venue templates break that rule that hardcoding the direction loses real pairings, so the other side is searched only if the conventional one finds nothing, at a tighter limit: 220 pt then 90 pt.

→

Nearest wins

Two figures on a page do not both get the same caption. A tolerance of -6 pt allows for a caption's glyph box overhanging the rule that starts a table.

→

It travels

The caption is stored on the figure or table, so it goes into the chunk, the index and the prompt with it, rather than sitting nearby as unrelated text.

4  Display equations, found by what is absent

The obvious test, "does this line use a maths font", does not work: in a LaTeX paper the body font and the maths fonts are mixed constantly inside ordinary prose, because every inline symbol is set in one. Both lines below are from page 4 of "Attention Is All You Need".

Prose, with symbols in it

fonts = CMMI10, CMMI7, NimbusRomNo9L-Regu

"queries and keys of dimension dk, and values of dimension dv. We compute"

A maths font is present. This is a sentence.

A display equation

fonts = CMMI10, CMMI7, CMR10

"Attention(Q, K, V ) = softmax(QKT"

No body font anywhere on the line. That is the discriminator.

Detection

parse/formulas.py

Nearly free: the fonts are already counted

The test

The line's fonts intersected with the body font set must be empty. The census was already collected for heading detection, so this costs nothing extra.

→

Confirm it is maths

At least 4 characters, and either a maths glyph or ≥ 40% of characters in a maths font, plus a relation: one of = ≠ ≤ ≥ ∈ ⊂ ∼ ∝ → ⇒ and the rest.

→

Reject the lookalikes

Angle brackets are relations, so <pad>, <EOS> and </> are matched as token tags and thrown out.

U+2217 is deliberately not a maths glyph here: it is the author footnote marker.

→

Shape and number

Set in from the margin and not running past 92% of the body width. A trailing (1), (3.2) or (A.4) becomes the label.

Two equations do not merge into one. Consecutive formula lines are allowed a looser vertical gap, line_height × 2.5 rather than × 0.9, because a multi-line equation is set with wide leading and the ordinary gap test splits one equation into three. What this does not do is recover LaTeX: getting \frac{QK^T}{\sqrt{d_k}} back from glyph positions is a research problem, and the deep tier's formula enrichment is the right tool. The text, the box and the number are enough to find it, cite it, show it and hand the region to a vision model.

5  References and the citations that point at them

Split the list

parse/citations.py → split_references

One element into many

The problem

A reference list is one run of lines in one font, so the grouper reads it as a single element: [1] Ba ... 2016. [2] Bahdanau. Every entry is individually unreachable.

→

Split on the marker

A bracketed number, a bare number and a stop, or, in an author-year list, a new surname starting a line.

→

Shallow metadata

Number, year, title and authors, deliberately no more. Anything deeper is better answered by resolving the entry than by parsing it.

→

Sections first

Splitting applies only inside the references section, so it has to run after _attach_sections and before order is reassigned.

Link the markers

citations.py → link_markers

Two styles, both wanted

Numeric

[13], [12, 13], [4-7] resolve by the entry's own number, ranges expanded.

→

Author-year

(Vaswani et al., 2017) resolves on first surname plus year, which is the pair the style guarantees unique within one bibliography.

→

Why both

A library will hold papers in both styles, and a reader following a claim to its source does not care which the author used.

→

Result

An in-text marker becomes a link to the entry, and the entry knows which passages cite it.

Resolve to something openable

server/refs.py

Three sources, in order of certainty

1. What it already says

A DOI or arXiv id printed in the entry resolves with no lookup at all, which covers most of machine learning. Free, and done when the page loads.

→

2. arXiv, by title

Free, no key, no registration. Accepted at 82% title overlap.

→

3. Crossref, by title

Free, no key, asks only that you identify yourself, which USER_AGENT does.

→

View, then Add

Lookup is a button, not automatic: it is one request per entry and a reference list is long. Add appears only where a free PDF exists, because offering a download that leads to a paywall is worse than offering none.

6  Optional passes: OCR, and rendering a page

OCR, off by default

parse/ocr.py

Two jobs, one engine

Scanned pages

A page with an empty text layer is a photograph of a page. Without this such a paper indexes as nothing at all and silently returns no results for every query.

→

Text inside figures

A chart's axis labels and data labels are frequently the only place a number appears in the whole paper. "What was the accuracy at epoch 50" is answerable from the figure and nowhere else.

The highest value use of OCR in a paper reader, and the one most systems skip.

→

Engines, in order

RapidOCR on onnxruntime, no system binary and no torch, the only one that could run on a slim deployment. Then EasyOCR, then Tesseract.

→

Why off

Slow, and wrong often enough on a dense figure to be worth a user's decision. On a paper with a good text layer it adds nothing.

Page images

server/pages.py

On demand, never at ingest

Measured, not assumed

On a 26 page paper: 38 ms and 227 KB per page at PAGE_RENDER_SCALE = 1.6, against 8.3 MB for the PDF itself.

→

So: lazily

Rendering every page eagerly is unnecessary rather than expensive. A page is rendered the first time it is asked for, and the digest is written back onto the paper's page list.

→

Locked per page

Two requests for the same page do not render it twice: the second waits, then re-reads and finds the work done.

→

What it is for

The reader overlay. Boxes drawn in percentages of the page's own point dimensions, so a wrong table or a missed heading is visible rather than merely recorded.

8  How much to trust one parse

The parser already knows how well it did. It records whether a table's columns were read from ruling or inferred, whether a figure was an image object or a cropped guess, whether a page had a text layer, and whether a caption was ever matched. None of that was ever shown, so a bad parse looked exactly like a good one and a wrong number in a table looked as authoritative as a right one.

Weighted worst

parse/quality.py

A table whose columns were guessed. The numbers look fine and are in the wrong columns, which is the failure most likely to mislead a reader who cannot tell.

Most complete

A page with no text layer. Total, but at least obvious: nothing from that page appears anywhere, and the concern names OCR as the fix.

Untidy and harmless

A figure with no caption attached. Counted and reported, weighted low, because nothing about it is misleading.

The concerns are the point

The score is a summary. What is actually useful is the list naming what is likely wrong and what to do about it, shown on the paper and in the library as a badge.

9  The deep tier, where it is available

Docling was chosen over Marker and MinerU deliberately, and not because it wins on raw accuracy. On olmOCR-bench as of 2026 Marker 2 leads at 76.0, MinerU is at 72.7 and Docling's non-VLM pipeline is at 50.3.

Licence decides it

MIT and Linux Foundation governance. Marker's weights carry a commercial restriction and MinerU is AGPL, which settles the question for anything a user may want to deploy.

A document, not markdown

A structured DoclingDocument with pages, boxes and reading order. This whole application is built on those, and reconstructing them from markdown is a downgrade.

Runs on a CPU

A real CPU path, where the other two assume a GPU. An optional VLM backend, granite-docling at 258M, closes most of the gap in 4 GB of VRAM.

What it adds

TableFormer reads spanning cells and nested headers the fast tier cannot, finds tables with no ruling at all, and enriches formulas. Adding a fourth parser means editing registry.py and nothing downstream.
